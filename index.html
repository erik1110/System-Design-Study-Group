單一伺服器

    SHEET 02

    起點：單一伺服器

    千里之行，始於單一伺服器。Web App、資料庫、快取通通擠在同一台機器上。

    請求流程：

    • 使用者透過網域名稱（例如 api.mysite.com）造訪網站，DNS 通常是跟第三方付費購買的服務，並非自己架設。
    • DNS 回傳一組 IP 位址給瀏覽器或 App。
    • 瀏覽器 / App 直接對這個 IP 發出 HTTP 請求。
    • 伺服器回傳 HTML 頁面或 JSON 給前端渲染。

    流量的兩個來源：

    網頁應用程式
    伺服器端語言（Java、Python…）處理商業邏輯與儲存；前端用 HTML／JavaScript 負責畫面呈現。
    行動應用程式
    Mobile App 與伺服器之間用 HTTP 溝通，API 回應多半採用 JSON 格式，簡單又通用。
    SHEET 03

    使用者變多之後：資料庫要分家

    一台伺服器不夠用時，先把「網頁／行動流量」跟「資料庫」拆成兩台機器，讓兩層可以各自獨立擴展。接著要決定：用關聯式還是非關聯式資料庫？

    比較項目關聯式資料庫（RDBMS / SQL）非關聯式資料庫（NoSQL）
    代表產品MySQL、Oracle、PostgreSQLCouchDB、Neo4j、Cassandra、HBase、DynamoDB
    資料型態表格與列（rows），支援 JOINKey-Value、Graph、Column、Document 四大類，通常不支援 JOIN
    適合情境大多數應用的預設選擇，40 年來驗證穩定需要超低延遲、資料無結構、只需序列化 (JSON/XML/YAML)、資料量極大時考慮

    筆記重點：先選 SQL，除非你的情境明確落在 NoSQL 更適合的四種狀況之一。

    SHEET 04

    垂直擴展 vs 水平擴展

    垂直擴展（Scale Up） — 幫同一台機器加 CPU / RAM。

    • 流量還小時很好用，設定簡單。
    • 硬體有極限，不可能無限加大。
    • 沒有容錯／備援：這台掛了，網站就整個掛了。

    水平擴展（Scale Out） — 把資源池裡的伺服器一台一台加進去。

    • 大型應用的長期解法，理論上沒有上限。
    • 需要搭配負載平衡器才能發揮效果。
    • 是後面所有擴展手法的基礎。
    SHEET 05

    負載平衡器：解決單點故障

    使用者改連負載平衡器的公開 IP，Web 伺服器則只用內網 IP（Private IP）互相溝通，不再直接暴露給外部。

    使用者
    →
    負載平衡器
    公開 IP
    →
    Web 伺服器 1
    Web 伺服器 2
    • 其中一台掛掉：流量全部轉給另一台，網站不會整個離線；同時補一台健康的伺服器進池子。
    • 流量暴增：只要往伺服器池加機器，負載平衡器會自動開始分流過去，不用改架構。
    SHEET 06

    資料庫複製：Master / Slave

    Web 層解決了單點問題，資料庫也要如法炮製 — 一個主（Master）負責寫入，多個從（Slave）負責讀取；讀多寫少，所以從資料庫通常比主資料庫多。

    主資料庫
    寫 / 改 / 刪
    ⇢ 非同步複製 ⇢
    從資料庫 1
    只讀
    從資料庫 2
    只讀

    好處：

    • 效能：寫入集中在主節點，讀取分散到多個從節點，可平行處理更多查詢。
    • 可靠性：就算某座機房被天災摧毀，資料仍在其他地點保存著。
    • 高可用：某台資料庫離線，還能從其他節點存取資料。

    容錯情境：從資料庫掛了 → 讀取暫時導回主資料庫，同時換一台新的從資料庫頂上。主資料庫掛了 → 提升一台從資料庫成為新主，這個過程在正式環境比較複雜，因為從節點資料可能還沒跟上最新進度。

    SHEET 07

    快取層：別讓資料庫每次都被打

    快取是暫存區，把「昂貴查詢的結果」或「常被存取的資料」放進記憶體，讓後續請求更快拿到答案。

    Web 伺服器
    →
    先查快取
    命中？
    ✓ 直接回傳
    ✗ 查資料庫→寫回快取→回傳

    這種「先查快取，沒有才查資料庫」的策略叫做 read-through cache。

    使用快取前要想清楚的五件事：

    • 什麼時候該用：資料「常讀、少改」最適合；快取資料活在揮發性記憶體，重要資料還是要有持久化儲存，因為快取伺服器重開機資料就沒了。
    • 過期策略：太短 → 一直重新從資料庫載入；太長 → 資料容易過時。要抓一個平衡點。
    • 一致性：資料庫和快取的寫入不是同一個交易，容易不同步；跨區域規模化時更難維持一致，可參考 Facebook《Scaling Memcache》論文。
    • 容錯：單一快取伺服器是單點故障（SPOF）；建議跨機房部署多台快取，並預留額外記憶體緩衝。
    • 淘汰策略：快取滿了要踢掉誰？最常見是 LRU（最近最少使用），也可以用 LFU（最少使用次數）或 FIFO。
    SHEET 08

    CDN：把靜態資源搬到離使用者最近的地方

    CDN 是分佈在世界各地的伺服器網路，專門快取圖片、影片、CSS、JS 這類靜態內容。離 CDN 節點越遠，網頁載入越慢。

    使用者 A 要 image.png
    →
    CDN 節點
    • CDN 節點沒有快取 → 回源站（Web 伺服器或 S3）拿檔案。
    • 來源站回傳圖片，並附上 TTL（Time-to-Live）標示快取多久。
    • CDN 存好快取後回傳給使用者 A；TTL 過期前都用快取版本。
    • 使用者 B 要同一張圖 → TTL 沒過期的話，直接從 CDN 快取拿，不用再問源站。

    使用 CDN 要注意：

    • 成本：CDN 按流量計費，不常被存取的資源放著沒什麼好處，可以考慮移出。
    • 過期時間：太長內容不新鮮，太短造成頻繁回源。
    • 容錯：CDN 短暫故障時，前端要能偵測並改向源站要資源。
    • 提前失效：可以呼叫 CDN 廠商 API 主動清除，或用「物件版本化」（如 image.png?v=2）逼出新版本。
    SHEET 09

    無狀態網頁層

    要水平擴展 Web 層，得先把「狀態」（例如 session）搬出伺服器本身。

    Stateful（有狀態）

    使用者 A 的 session 存在伺服器 1 上 → A 的請求一定要被路由回伺服器 1，否則驗證失敗。通常靠負載平衡器的「黏性連線（sticky session）」硬撐。

    • 加減伺服器很麻煩
    • 單台故障處理困難

    Stateless（無狀態）

    Session 資料搬到共享儲存（關聯式資料庫、Memcached/Redis 或 NoSQL）。任何一台 Web 伺服器都能處理任何使用者的請求。

    • 系統更簡單、更穩固
    • 可以依流量自動增減伺服器（Auto Scaling）
    SHEET 10

    多資料中心

    使用者遍布全球後，一座機房不夠。用 geoDNS 把使用者導到最近的機房；某座機房整個掛掉時，全部流量改導去健康的那一座。

    使用者
    →
    geoDNS 路由
    ↙
    機房 US-East
    x% 流量
    ↘
    機房 US-West
    (100-x)% 流量

    要解決的三個難題：

    • 流量導向：靠 geoDNS 依使用者地理位置導到最近機房。
    • 資料同步：各地機房用不同的本地資料庫／快取，容易在 failover 時導到沒有資料的機房 — 常見做法是跨機房複製資料。
    • 測試與部署：要在不同地點測試，並用自動化部署工具讓各機房服務版本一致。
    SHEET 11

    訊息佇列：把元件解耦

    訊息佇列是支援非同步通訊的緩衝區。生產者（Producer）發訊息進佇列，消費者（Consumer）獨立把它拿去處理 — 兩邊互不需要同時在線。

    Web 伺服器
    Producer
    → 發佈任務 →
    訊息佇列
    → 領取任務 →
    處理 Worker
    Consumer

    舉例：使用者上傳照片要裁切、加銳利、模糊化，這些耗時工作交給 Worker 非同步處理。佇列變長就多加幾台 Worker，佇列空了就縮減，生產者與消費者可以各自獨立擴展。

    SHEET 12

    日誌、監控與自動化

    系統還小的時候可有可無，變成大型業務之後就是必需品。

    日誌 Logging
    監控錯誤日誌，可用單機層級或集中式服務彙整，方便搜尋查看。

    自動化 Automation
    系統變大變複雜就需要 CI/CD：每次提交都自動驗證，提早抓出問題；建置／測試／部署流程自動化能大幅提升生產力。

    指標 Metrics

    • 主機層級：CPU、記憶體、磁碟 I/O
    • 彙整層級：整個資料庫層、快取層的表現
    • 商業指標：日活躍使用者、留存率、營收
    SHEET 13

    資料庫擴展：分片（Sharding）

    垂直擴展資料庫終究撞到硬體上限、成本又高、單點故障風險也大。水平擴展資料庫 = 分片：把大型資料庫切成多個 Shard，各自結構相同，資料各自獨立。

    user_id % 4
    →
    Shard 0
    Shard 1
    Shard 2
    Shard 3

    挑選 Sharding Key（分片鍵）最重要的原則：能讓資料平均分佈。

    分片帶來的新麻煩：

    • 重新分片：單一 shard 資料塞爆，或資料分佈不均導致某些 shard 提早爆滿，就得調整分片函式並搬移資料 — 第五章的一致性雜湊（Consistent Hashing）就是為了解決這個問題。
    • 名人問題（Hotspot Key）：假設 Katy Perry、Justin Bieber、Lady Gaga 的資料剛好都落在同一個 shard，這個 shard 的讀取量會被灌爆 — 可能得為每位「名人」單獨配一個 shard，甚至再進一步切分。
    • JOIN 與反正規化：資料庫一旦分片，跨 shard 做 JOIN 很困難，常見解法是把資料反正規化（denormalize），讓查詢能在單一表內完成。
    SHEET 14 — 課外補充

    業界真實案例：把書裡的觀念對照到真實世界

    以下三個例子不是書裡的內容,是我額外找的補充教材,分別對應「CDN」「資料庫複製」「資料庫分片」三個小節,點開看細節就好,不看也不影響你理解本章。

    案例 01
    Netflix Open Connect — 自己蓋一座 CDN
    對照 SHEET 08．CDN
    +

    主動預先分發Netflix 沒有租第三方 CDN,而是把自製的專用機器 OCA（Open Connect Appliance）直接放進全球超過六千個 ISP 的機房裡。跟書中「使用者要圖片、CDN 沒快取才回源站」的被動流程不同,Netflix 是反過來:在離峰時段,依照預測模型先把「這個地區可能會紅的內容」預先搬進 OCA,使用者按下播放時幾乎不用等現抓。

    控制面／資料面分離OCA 平常會回報健康狀態、可連通性給中央的快取控制服務;但如果 OCA 一時連不上中央系統,它仍然可以憑「上一次拿到的設定」繼續把已經快取好的內容送給正在收看的使用者,只是內容目錄暫時不會更新。這是一種很實用的容錯設計:平常依賴中央協調,斷線時退化成「自己顧自己」也還能動。

    流量怎麼導哪些使用者流量會被導去哪一台 OCA,是 ISP 透過 BGP 網路協定明確宣告出來的,不是 OCA 自己搶流量。這讓 ISP 對自己的網路仍保有完全的控制權。

    對理解本章的幫助:CDN 不是只有「快取一份靜態檔案」這麼簡單,規模夠大時,「预测+预先分发」加上「控制面／資料面分離」是更進階的容錯思路。

    案例 02
    GitHub 2018 資料庫故障轉移事故
    對照 SHEET 06．資料庫複製
    +

    起因很小2018 年 10 月 21 日,GitHub 東岸機房在例行維護中,跟網路樞紐的連線斷了短短 43 秒 — 這就是書裡說的「網路分區（network partition）」。

    自動容錯轉移的兩難GitHub 用一套叫 Orchestrator 的工具自動管理 MySQL 主從架構與容錯移轉。它偵測到東岸主資料庫失聯,依照多數決機制,把西岸的一台從資料庫拔升成新的主資料庫。問題是:斷線的這 43 秒裡,東岸主資料庫其實還在繼續接受寫入,但這些寫入根本來不及同步過去給西岸。等連線恢復、應用程式開始改寫去新的西岸主資料庫時,兩邊的資料已經「分岔」了,沒辦法乾淨地合併回去。

    最後的取捨GitHub 面臨書裡提過的經典抉擇：要一致性,還是要可用性？他們選擇優先保住資料不遺失、不衝突 — 讓網站顯示過時資訊、變成唯讀模式,足足花了 24 小時手動核對、補齊差異資料,而不是冒著使用者資料衝突或遺失的風險強行切回。

    對理解本章的幫助:書中提到「正式環境拔升新主更複雜,因為從資料庫可能還沒同步到最新進度」,這起事故就是最直接的真實案例 — 越自動化的容錯機制,越需要想清楚「資料還沒同步完」的那個空窗期怎麼辦。

    案例 03
    Instagram 的「邏輯分片」— 先切好,晚點再搬家
    對照 SHEET 13．資料庫分片
    +

    不換 NoSQL,分片 PostgreSQLInstagram 早期評估過幾種 NoSQL 方案,最後仍決定留在 PostgreSQL,靠「分片」硬撐過快速成長期。

    邏輯分片 ≠ 實體分片他們一開始就在程式碼邏輯上切出幾千個「邏輯分片」（用 Postgres 的 schema 功能實作,每個邏輯分片結構相同,各自放一份 users、photos 等資料表）,但這幾千個邏輯分片一開始其實全部擠在少數幾台實體機器上。等流量真的成長到撐不住,只需要把「一整批邏輯分片」搬去新機器,不必重新計算雜湊、不必重新切分資料 — 這正是書裡提到「resharding 很痛」的一種務實解法:先把切分的邊界定死,之後只搬「整批」,不用重新分配。

    ID 本身就帶分片資訊Instagram 設計了一組 64 位元 ID：41 位元時間戳記 + 13 位元邏輯分片編號 + 10 位元自增序號。這代表光看一個 ID,就能反推出「這筆資料在哪個分片」「大概什麼時候寫入的」,同時 ID 天生照時間排序 — 這個「用 ID 結構帶資訊」的手法,跟書中第七章要討論的 Twitter Snowflake ID 概念是同一個家族。

    對理解本章的幫助:分片的痛點不是「切」,是「以後要重新切」。Instagram 的做法示範了一種「先切細、晚點再搬」的思路,讓 resharding 從「重新計算」變成「搬家」。

    SHEET 15 — 最終蓋章

    百萬使用者以後：本章重點回顧

    擴展系統是一個不斷迭代的過程；下面八點，是撐起百萬使用者規模的核心心法。

    • 網頁層保持無狀態（Stateless）
    • 每一層都要有備援（Redundancy）
    • 能快取的資料盡量快取
    • 支援多個資料中心
    • 靜態資源放上 CDN
    • 資料庫用分片（Sharding）擴展
    • 把各層拆成獨立服務
    • 監控系統並善用自動化工具
